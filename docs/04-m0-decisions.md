## 1. WG-001 业务决策冻结

以下决策已冻结，任何一项变更都会影响数据库关系、密钥格式或礼品展示结构，需重新评审。

| 编号 | 决策 | 冻结结论 |
|---|---|---|
| D-01 | 姓名唯一性 | 所有朋友本名全局唯一，不设计同名识别、提示或分流。 |
| D-02 | 本名与昵称归并 | 每位可登录成员至少配置本名；可另配置零到多个昵称。本名与全部昵称映射到同一成员，不复制用户，不产生多份礼品。 |
| D-03 | 登录名称唯一 | 所有登录名称（本名 + 昵称）规范化后全局唯一；昵称不得与任何其他成员的本名或昵称冲突。 |
| D-04 | 登录匹配方式 | 仅做确定性精确匹配（规范化后相等），不做拼音、繁简、错别字或近似匹配。 |
| D-05 | 密钥格式 | 卡片密钥严格为 8 位 ASCII 数字，正则 `^[0-9]{8}$`；不忽略空格/连字符/字母/全角数字。 |
| D-06 | 密钥来源 | 密钥由项目所有者人工生成，系统只校验、导入、摘要存储，绝不生成、打印或导出。 |
| D-07 | 密钥存储 | 明文密钥不入库；数据库仅存 `HMAC-SHA256(K_access_lookup, rawKey)` 摘要。 |
| D-08 | 绑定约束 | 一个密钥最多绑定一个同行组；一个同行组可绑定多个密钥，同组任一已绑定密钥看到同一份回礼。密钥侧由绑定事务的条件更新保证，同行组侧不设唯一约束。（2026-09-13 修订：原为同行组侧也唯一，放宽以防登录名称被冒名首绑后本人无法补绑。） |
| D-09 | 首次绑定语义 | 有效登录名称 + 有效未绑定未停用密钥首次组合，在单事务内建立该成员所属同行组与密钥的绑定并建会话。 |
| D-10 | 已知误绑风险 | 接受"首次输入他人姓名可能误绑"的低概率风险；不做身份证明、预绑定或自动纠错。误绑由所有者停服后人工修正。 |
| D-11 | 同行组统一建模 | 单身/夫妻/夫妻带娃统一为"同行组 + 成员"，运行时不写家庭形态分支逻辑；成员可配置是否可登录。 |
| D-12 | 多礼品 | 一个同行组可配置一到多份礼品；同一密钥登录后展示该组全部礼品，按 `ordinal` 排序。 |
| D-13 | 礼品类型 | 首批为旅游年卡（长三角/京津冀/广东，各含主人与同行变体）、电影券（`movie_voucher`）、咖啡券（`coffee_voucher`）。类型完全由数据文件驱动，无内置必备清单，新增或细化类型不改鉴权与校验逻辑。兑换入口支持 HTTPS URL 与微信小程序口令（`#小程序://名称/路径`）两种形态。 |
| D-14 | 礼品类型默认与覆盖 | 礼品类型提供默认兑换说明/有效期/链接；礼品实例可逐字段覆盖。 |
| D-15 | 礼品码存储 | 礼品凭证（激活码，或卡号+密码）使用 AEAD（AES-256-GCM）加密，每条独立随机 nonce；明文不入库、不进日志、不进 URL。凭证形态由礼品实例 `credential_mode` 决定：`code` 单一激活码 / `card_secret` 卡号+密码（D-15 修订，2026-09-15）。 |
| D-16 | 会话 | 服务端随机令牌（≥256 bit），库存 SHA-256 摘要；Cookie `wedding_session`，Secure/HttpOnly/SameSite=Lax，Path 由 nginx 收编到 `/wedding/`。 |
| D-17 | 备份 | 本机 cron 独立单元 `/etc/cron.d/wedding`，每小时 `:44`，SQLite online backup，保留最近 72 份，只写 `/data/wedding/backups/`。 |
| D-18 | 异常处理边界 | 少量异常一律停服后人工检查修正，不建设自动补发、改绑、审计状态机或告警平台。 |
| D-19 | 目录收束 | 全部产出集中于 `/root/WeddingGift/`（代码/部署物）与 `/data/wedding/`（运行时数据）；日志走 Docker json-file。 |
| D-20 | 数据隔离 | 不使用/探测/挂载 Costra 任何有状态组件、配置与备份；应用只用自有 SQLite 与自有目录。 |

**开放项处置**：M0 结束时不存在会改变数据库关系、密钥格式或礼品展示结构的未决问题。最终文案（新人称呼、婚礼日期、致谢文本）为可延后确认项，见第 3 节，其字段已冻结，不阻塞 M1/M2。

## 2. WG-002 数据契约冻结

六类数据实体：同行组、成员、登录名称、礼品类型、礼品实例、卡片密钥。字段定义对齐技术架构 §6 的 ER 模型；导入文件字段与数据库字段区分：**导入文件承载明文与业务外部编号，数据库落地时把密钥转 HMAC 摘要、礼品码转 AEAD 密文**。

### 2.1 术语与通用约定

- `external_ref`：业务侧稳定外部编号（如 `G001`、`M001`、`GI001`、`K001`），用于导入引用与状态报告，不含敏感信息，可进 Git 虚构样例。
- 规范化（登录名称）：去首尾空白 → Unicode NFC →（未来拉丁字母统一大小写）；不删内部字符、不做近似匹配。
- 时间统一 UTC。
- 文件编码统一 UTF-8（无 BOM）。CSV 首行为表头；密钥/礼品码字段按文本读取，禁止被表格转成科学计数法或丢前导零。

### 2.2 同行组 recipient_group

| 字段 | 类型 | 必填 | 约束 / 说明 |
|---|---|---|---|
| external_ref | text | 是 | 全局唯一，如 `G001` |
| salutation | text | 是 | 组称呼，如"张伟 & 李娜 一家" |
| custom_message | text | 否 | 组专属致谢短句；空则用全局致谢语 |
| status | text | 是 | `active` / `disabled` |

### 2.3 成员 member

| 字段 | 类型 | 必填 | 约束 / 说明 |
|---|---|---|---|
| external_ref | text | 是 | 全局唯一，如 `M001` |
| group_external_ref | text | 是 | 引用同行组 external_ref |
| display_name | text | 是 | 展示用本名；规范化后全局唯一（即本名 login name） |
| can_login | boolean | 是 | `true` 可登录（成年人等）；`false` 仅展示（如儿童） |
| sort_order | integer | 是 | 组内展示顺序，从 1 起 |

约束：每个 `active` 同行组至少一名 `can_login=true` 成员；成员本名自动作为一条 `kind=real_name` 的登录名称。

### 2.4 登录名称 member_login_name

| 字段 | 类型 | 必填 | 约束 / 说明 |
|---|---|---|---|
| member_external_ref | text | 是 | 引用成员 external_ref |
| value | text | 是 | 登录名称原文（本名或昵称） |
| kind | text | 是 | `real_name` / `nickname` |

约束：规范化后全局唯一；每位 `can_login=true` 成员必须恰好有一条 `real_name`（与该成员 `display_name` 一致），昵称条数不限（含 0）；`can_login=false` 成员可不配置登录名称。

### 2.5 礼品类型 gift_type

| 字段 | 类型 | 必填 | 约束 / 说明 |
|---|---|---|---|
| type_key | text | 是 | 主键，如 `travel_csj_first` |
| title | text | 是 | 展示标题，如"旅游年卡" |
| subtitle | text | 否 | 副标题 |
| default_instructions | text | 是 | 默认兑换说明 |
| default_validity_text | text | 否 | 默认有效期文案 |
| default_redemption_url | text | 否 | 默认兑换入口，必须为 HTTPS URL 或微信小程序口令（`#小程序://名称/路径`） |
| theme_variant | text | 否 | 视觉变体标识 |

首批类型见 §3.2；礼品类型完全由数据文件驱动，导入校验不强制任何必备 type_key。

### 2.6 礼品实例 gift_item

| 字段 | 类型 | 必填 | 约束 / 说明 |
|---|---|---|---|
| external_ref | text | 是 | 全局唯一，如 `GI001` |
| group_external_ref | text | 是 | 引用同行组 external_ref |
| type_key | text | 是 | 引用礼品类型 |
| credential_mode | text | 是 | 凭证形态：`code` 单一激活码 / `card_secret` 卡号+密码 |
| code_plaintext | text | 是 | 凭证明文（`code` 模式为激活码；`card_secret` 模式为卡号）。仅导入文件，落库转 AEAD 密文；不进 Git 真实数据 |
| secret_plaintext | text | 条件 | 密码明文（仅 `card_secret` 模式必填；`code` 模式必须为空）。仅导入文件，落库转 AEAD 密文 |
| instructions_override | text | 否 | 覆盖类型默认兑换说明 |
| validity_text_override | text | 否 | 覆盖默认有效期 |
| redemption_url_override | text | 否 | 覆盖默认兑换入口，必须为 HTTPS URL 或小程序口令 |
| ordinal | integer | 是 | 组内礼品展示顺序，从 1 起 |
| status | text | 是 | `active` / `disabled` |

约束：每个 `active` 同行组至少一份 `active` 礼品；`type_key` 必须存在；激活码/卡号（`code_plaintext`）全局唯一，密码不做唯一要求；覆盖链接与默认链接均须 HTTPS。

### 2.7 卡片密钥 access_key

| 字段 | 类型 | 必填 | 约束 / 说明 |
|---|---|---|---|
| external_ref | text | 是 | 全局唯一，如 `K001` |
| code_plaintext | text | 是 | 8 位数字明文（仅导入文件，落库转 HMAC 摘要；不进 Git 真实数据） |
| status | text | 是 | `active` / `disabled` |
| bind_group_external_ref | text | 否 | 预留：一般为空，导入时不预绑定；绑定由运行时首登产生 |

约束：`code_plaintext` 严格 `^[0-9]{8}$` 且全局唯一；`key_digest` 全局唯一；导入默认不预绑定（`group_id` 空）。

### 2.8 虚构样例覆盖矩阵

`testdata/fixtures/` 下的虚构数据包覆盖以下全部场景（不含同名场景）：

| 场景 | 覆盖对象 |
|---|---|
| 单身 | 一个组一名可登录成员 |
| 夫妻 | 一个组两名可登录成员 |
| 夫妻带娃 | 一个组两名可登录成人 + 一名 `can_login=false` 儿童 |
| 一个成员多昵称 | 某成员配置 2+ 个昵称 |
| 三个礼品类型 | 三类各至少出现一次 |
| 一个组多份礼品 | 某组配置 2+ 份礼品并含 ordinal 排序 |
| 实例级覆盖 | 至少一份礼品覆盖默认兑换说明/有效期/链接 |
| 卡片密钥 | 全部 8 位唯一数字，导入不预绑定；密钥数量可多于同行组数量（同组可绑定多个密钥） |

## 3. WG-003 文案字段与占位内容

文案由配置驱动，M1/M2 使用占位文本即可实现与验证；真实文案在 M3–M4 并行确认，不硬编码进组件逻辑。

### 3.1 文案字段清单（全局配置）

| 字段 | 用途 | 默认值 |
|---|---|---|
| couple_names | 新人称呼（登录后作为落款居右，署名定稿） | 「赵伟 & 刘子璇」 |
| wedding_date | 婚礼日期展示（落款署名之下） | 「2026-09-26」 |
| home_intro | 主页/落地页引导短文案 | 「感谢你来见证我们的幸福时刻」 |
| login_hint | 登录页提示（用自己的名字 + 8 位密钥） | 「请输入你的名字，以及卡片上的 8 位数字」 |
| thanks_message | 全局致谢语（组无 custom_message 时使用） | 「谢谢你的祝福，这是我们为你准备的小小心意」 |
| privacy_note | 隐私短说明 | 「本页仅用于展示回礼，我们只收集识别所需的信息，活动结束后删除。」 |
| contact_hint | 联系/客服提示 | 「如有疑问，请咨询赵伟/刘子璇。」 |
| icp_filing_text | 备案号展示文本 | 「沪ICP备2026017253号-2」 |
| icp_filing_url | 备案链接 | 「https://beian.miit.gov.cn/」 |
| maintenance_text | 维护/到期状态文案 | 「页面维护中，请稍后再试。」 |

### 3.3 占位内容使用约束

- M1 占位主页只呈现"链路验证"信息，不含真实新人姓名、日期或任何业务数据。
- 文案字段以配置/模板变量形式存在，不写死在处理逻辑分支中。
- 真实文案替换只改配置与展示文本，不改路由、鉴权与数据模型。
