## 1. 文档目的

本文档沉淀 WeddingGift 的背景、已确认业务规则、项目边界和部署硬约束，作为后续产品设计、技术设计、开发和验收的共同事实源。

事实源优先级：

1. 项目所有者后续明确确认的新决定；
2. 本文档记录的业务基线；
3. `staging-machine-brief.md` 记录的共享服务器约束；
4. 其他设计文档和实现细节。

若业务需求与共享服务器红线冲突，必须先调整 WeddingGift 方案，不得绕过服务器红线。

## 2. 项目背景

项目所有者即将举办婚礼，计划向到场朋友赠送实体回礼卡。每张实体卡包含：

- 指向 `https://stg.costra.cloud/wedding/` 的二维码；
- 一串由项目所有者生成的 8 位纯数字密钥。

朋友扫码进入网页，输入自己的本名或日常昵称，以及卡片密钥。鉴权成功后，网页展示为该朋友所在同行组准备的礼品列表及激活码。

首批礼品类型暂定为：

- 旅游年卡；
- 电影券；
- 咖啡券。

礼品类型必须由配置驱动，未来增加其他礼品类型时不修改登录和绑定流程。同一密钥可能对应多份礼品。

服务仅面向不超过 50 位朋友，预计运行约 3 个月，以手机和微信内置浏览器访问为主。

## 3. 项目目标

### 3.1 核心目标

1. 让来宾凭“本名或已配置昵称 + 8 位卡片密钥”顺畅地查看自己的礼品。
2. 支持单身、夫妻、夫妻带娃等同行结构，不把家庭形态写成分支硬逻辑。
3. 同一成员的本名和零到多个昵称均指向同一用户；同组成员使用组内唯一密钥看到相同礼品列表。
4. 一个密钥最多绑定一个同行组，一个同行组最多绑定一个密钥。
5. 一个同行组可配置一份或多份礼品，礼品类型可继续扩展。
6. 先完成真实 URL 下的最小主页访问链路，再继续开发数据、鉴权和礼品功能。
7. 在共享腾讯云机器上以简单、低资源、可回滚、可拆除的方式运行，不影响既有 Costra 服务和生产热备数据。

### 3.2 成功标准

- `https://stg.costra.cloud/wedding/` 能先展示无真实数据的最小主页，证明浏览器、HTTPS、nginx、Docker 网络和应用链路可达。
- 已配置来宾可以用本名或任一配置昵称登录，并查看、显示和复制本组全部礼品激活码。
- 同一成员的不同登录名称得到相同身份；不同成员的任何登录名称不会互相冲突。
- 同一同行组中的任一可登录成员均可使用该组唯一密钥登录。
- 已绑定密钥不能访问其他组；已有密钥的同行组不能再绑定第二个密钥。
- 未授权请求无法取得礼品激活码；接口和日志不泄漏明文卡片密钥或礼品码。
- 页面适合手机和微信内置浏览器，资源轻量，不依赖大图、视频、外部字体或第三方统计脚本。
- 应用容器硬内存上限不超过 256 MB、CPU 上限不超过 0.5 核，不向宿主机发布新端口。
- 本机 cron 能定时把 SQLite 数据库一致性备份到 WeddingGift 自有目录并按数量轮转。

## 4. 角色与核心概念

| 概念 | 定义 |
|---|---|
| 来宾成员 | 一位真实朋友；每位成员的本名在本项目名单中唯一，且只属于一个同行组 |
| 同行组 | 共用同一个卡片密钥、一组礼品和致谢内容的逻辑单位；单身、夫妻、夫妻带娃统一建模 |
| 登录名称 | 可用于登录的文本，包括成员本名和配置中的零到多个日常昵称；同一成员的全部登录名称映射到同一身份 |
| 卡片密钥 | 由项目所有者人工生成的 8 位 ASCII 数字；导入前不绑定任何同行组 |
| 绑定 | 某个有效密钥首次与有效登录名称组合成功后，与该成员所属同行组建立一对一关系的过程 |
| 礼品实例 | 一份具体礼品，包含类型和敏感激活码，并可覆盖该类型的默认兑换说明、有效期或链接；同一同行组可有多份 |
| 礼品类型 | 旅游年卡、电影券、咖啡券等展示配置；允许未来扩展 |
| 项目所有者 | 负责生成密钥、准备并导入名单与礼品、查看状态及处理少量异常的人 |

## 5. 已确认业务规则

### 5.1 姓名唯一，本名与昵称归并为同一用户

- 已确认所有朋友不存在本名同名，不设计重名识别、重名提示或重名分流。
- 每位可登录成员至少配置本名作为登录名称，也可以配置零到多个日常昵称。
- 本名和昵称只是同一成员的多个登录入口，不创建多个用户，也不产生多份礼品。
- 所有登录名称规范化后必须全局唯一；昵称不能与其他成员的本名或昵称冲突。
- 登录只做确定性匹配，不做拼音、错别字、近似字或模糊匹配。

### 5.2 密钥格式与来源

- 卡片密钥由项目所有者人工生成，系统不提供自动生成器。
- 密钥固定为 8 位 ASCII 数字，校验规则为 `^[0-9]{8}$`。
- 不自动忽略空格、连字符、字母或全角数字；前端可以按连续 8 位数字友好展示。
- 密钥原始清单由项目所有者在 Git 之外保管，通过受控数据文件导入。
- 后台分别校验登录名称和密钥；访客端统一返回模糊错误，避免枚举有效数据。

### 5.3 首次成功登录建立一对一绑定

当有效登录名称与有效、未绑定、未停用的密钥首次组合提交时：

1. 根据登录名称找到唯一成员及其同行组；
2. 确认该密钥尚未绑定，且目标同行组也尚未绑定其他密钥；
3. 在一个数据库事务中建立密钥与同行组的一对一绑定；
4. 创建登录会话；
5. 展示该同行组预先配置的礼品列表。

后续规则：

- 已绑定密钥配合同组任一成员的本名或配置昵称：登录成功。
- 已绑定密钥配合其他同行组的登录名称：登录失败。
- 未绑定密钥配合已拥有密钥的同行组登录名称：登录失败，且该密钥保持未绑定。
- 访客端不提供解绑或改绑能力；极少量误绑或数据错误由项目所有者停服后人工处理，不建设通用自动纠错、补发或审计状态机。

### 5.4 首次输入他人姓名的已知风险

实体卡初始不记名，系统无法判断密钥的物理持有人。如果某人使用自己的未绑定密钥输入另一位朋友的有效本名或昵称：

- 若对方同行组尚无密钥，该密钥会绑定到对方同行组；
- 若对方同行组已有密钥，本次登录失败，当前密钥保持未绑定；
- 误绑后访客无法自行改绑，项目所有者可按实际情况人工修正数据，并决定是否更换已经泄漏的礼品码。

本项目接受这一低概率风险，不增加身份证明、手机号、人工审批或预绑定关系。

### 5.5 同行组统一建模

运行时不针对“单身、夫妻、夫妻带娃”写不同业务逻辑：

- 单身：一个同行组，一名可登录成员；
- 夫妻：一个同行组，两名可登录成员；
- 夫妻带娃：一个同行组，两位可登录成年人和零到多个展示成员；儿童是否可登录由配置决定；
- 每位成员只属于一个同行组，因此一个成员最多使用该组唯一密钥；
- 同一组成员共享致谢主体和完整礼品列表。

### 5.6 一个同行组支持多份礼品

- 礼品在上线前分配到同行组，与后来绑定到该组的具体卡片密钥无关。
- 每个同行组可配置一份或多份礼品；同一密钥登录后展示该组全部礼品。
- 首批礼品类型为旅游年卡、电影券和咖啡券；新增类型只增加配置和必要展示文案，不修改鉴权逻辑。
- 系统只展示激活码和兑换说明，不代替第三方商家核销，也不判断激活码是否已在商家侧使用。

## 6. 产品范围

### 6.1 首版必须包含

- 通过真实 URL 访问的最小主页链路验证阶段；
- 手机优先的扫码落地页；
- 本名或配置昵称与 8 位卡片密钥登录；
- 首次一对一绑定与后续同组鉴权；
- 安全会话、退出登录和会话过期；
- 同行组个性化致谢文案；
- 多礼品列表、礼品类型、兑换说明、激活码遮罩、主动显示和复制；
- 友好但不泄漏校验细节的错误状态；
- 同行组、成员、登录名称、礼品、密钥的批量校验与导入；
- 密钥状态查询和停用；
- 基础运行日志、健康检查和本机 cron 数据库备份；
- 轻量化、无障碍基础支持、备案页脚和隐私说明；
- 共享机器上的容器化部署、回滚与到期拆除方案。

### 6.2 明确不做

- 同名用户识别、重名登录别名生成或重名分流；
- 系统自动生成卡片密钥；
- 访客注册、修改个人资料、手机号或短信验证；
- 通过姓名找回密钥；
- 微信登录、公众号授权或社交分享裂变；
- 支付、购物车、物流、礼品选择或换礼；
- 与礼品供应商同步核销状态；
- 公网 Web 管理后台；
- 自动补发、复杂凭据交付状态机或通用改绑流程；
- 独立业务审计平台、复杂审计保留策略或合规报表；
- COS/异机备份、主从数据库、高可用、RPO/RTO 承诺或自动灾难恢复；
- 多实例水平扩容、分布式数据库、Redis、消息队列；
- 为 WeddingGift 新增域名、证书、安全组端口或独立公网入口。

## 7. 非功能要求与简化原则

### 7.1 体验

- 视觉关键词：温馨、浪漫、简约、高级；避免模板化大红色婚庆风和过度动画。
- 单页完成主要流程；所有站内请求兼容 `/wedding/` 路径前缀。
- 主要触控目标不小于 44×44 px，表单有明确标签，支持减少动态效果偏好。
- 支持当前主流 iOS Safari、Android Chrome 和微信内置浏览器。

### 7.2 必要安全与隐私

- 全程 HTTPS；礼品激活码属于敏感数据，响应禁止缓存。
- 卡片密钥不以明文存入数据库；由于 8 位数字空间有限，必须使用带服务端秘密的 HMAC 摘要，不能使用可离线穷举的普通哈希。
- 日志禁止记录姓名原文、卡片密钥、礼品激活码、Cookie 和请求正文。
- 登录接口保留统一错误、基础来源校验、简单限流和事务绑定保护。
- 只收集完成礼品识别所需的数据，服务到期后删除在线数据。

### 7.3 小规模服务的简化边界

本项目没有性能、并发或数据量压力，也不要求高等级容灾和审计。设计原则是优先完成核心功能，避免为了理论场景引入额外开发和运维复杂度：

- 单实例、单 SQLite 数据库即可；不做主从、读写分离、缓存层或消息队列。
- 不设高并发性能指标，不做容量平台和复杂压测；只验证页面可用、事务约束正确和资源不超过共享机器上限。
- 不接 COS，不做跨机器备份、自动恢复、恢复纪元、故障切换或 RPO/RTO 承诺。
- 本机 cron 以独立单元 `/etc/cron.d/wedding` 落地（不改 Costra cron 文件），默认每小时 `:44` 创建一次 SQLite 一致性备份到 `/data/wedding/backups/` 并保留最近 72 份（≈3 天）；执行时间、频率和保留数量是上线前可调整的简单配置。
- WeddingGift 全部产出目录收束集中：`/root/WeddingGift/`（代码/compose/脚本/cron 与 nginx 片段仓库副本）与 `/data/wedding/`（运行时数据、备份、秘密、导入、nginx 改前备份）；应用日志走 Docker json-file，不散落其他位置。
- 本地备份与主库位于同一机器，整机或磁盘损坏时可能一起丢失；项目所有者明确接受该风险，必要时人工重建数据。
- 不建设独立审计表和复杂审计状态机；只保留脱敏运行日志和关键业务状态字段。
- 对少量异常优先采用停服后的人工检查与修正，不为极低频场景提前建设通用平台能力。

## 8. 共享服务器硬约束

本节只做摘要，完整规则以 `staging-machine-brief.md` 为准。该文档中的 Costra 主从、热备和生产副本是共享机器的既有事实，不是 WeddingGift 要建设的能力。

| 类别 | 必须遵守的约束 |
|---|---|
| 公网入口 | 仅使用 `https://stg.costra.cloud/wedding/`，由现有 `costra-nginx` 反代 |
| nginx | 只允许按原文纪律在 443 server block 增加 `/wedding/` 两个 location；修改前备份，修改后 `nginx -t` 并热加载，禁止重启 Costra nginx |
| 端口 | 应用只在 Docker 内网 `expose`，禁止 `ports:`，禁止申请新安全组端口 |
| 网络 | 以 external network 方式加入既有 `costra_default`；不得手工指定 Docker 网段 |
| 数据 | 绝对禁止使用或访问 Costra PostgreSQL、Redis、生产热备、备份和分析数据；只使用 `/data/wedding/` 自有目录 |
| 容器 | 独立 compose project；禁止 host network、privileged、docker.sock；仅挂载自有目录 |
| 资源 | 应用容器内存硬上限 ≤256 MB，CPU ≤0.5；每容器日志 `50m × 3` 轮转；`restart: unless-stopped` |
| 带宽 | 公网出口仅 1 Mbps，页面保持百 KB 级，不承载大图或视频 |
| 操作窗口 | 避开每天 00:00/06:00/12:00/18:00、06:27、23:50–24:00 的既有高峰任务 |
| 路径前缀 | 内部代理抹掉 `/wedding/`；前端链接、资源、请求和重定向不得错误落到域名根路径 |
| 合规 | 页面底部展示现有备案号并链接工信部备案网站；控制传播范围，不公开引流 |
| 拆除 | 约 3 个月后删除 WeddingGift location、容器、网络引用及自有数据目录，不触碰 Costra 其他资源 |

特别说明：该机器对 Costra 是 staging，但对 WeddingGift 将承载真实来宾和真实礼品码，因此仍需做好最小必要的访问控制、秘密管理、发布回滚和数据隔离；这不等于需要复制 Costra 的高可用与灾备体系。

### 8.1 既定接入方式的残余风险

1. **Docker 同网可达不等于网络隔离**：`wedding-app` 为让现有 nginx 反代而加入 `costra_default`，网络层可以到达同网容器。WeddingGift 不携带 Costra 凭据、不实现相关客户端或地址配置、不挂载其文件。
2. **路径隔离不等于浏览器同源隔离**：`/wedding/` 与 Costra 其他路径同属 `https://stg.costra.cloud`。上线前需确认根作用域 Service Worker、同源可执行内容和 Costra XSS 风险；若不可接受，只能重新决策独立 origin。

## 9. 已确认设计基线

1. 所有朋友本名唯一，不设计同名处理。
2. 每位可登录成员可使用本名和零到多个配置昵称；所有登录名称规范化后全局唯一。
3. 每位成员只属于一个同行组，每个同行组最多绑定一个密钥。
4. 密钥由项目所有者生成，严格为 8 位纯数字，系统只校验和导入。
5. 一个密钥最多绑定一个同行组；数据库同时约束密钥和同行组两侧唯一。
6. 每个同行组可配置一份或多份礼品；首批类型为旅游年卡、电影券、咖啡券。
7. 页面主语言为简体中文；二维码只包含带尾斜杠的统一网址。
8. 项目所有者通过服务器命令行管理数据，不开放公网管理页面。
9. 真实姓名、明文卡片密钥和明文激活码数据文件不进入 Git 仓库。
10. 开发早期先用虚构内容让真实 URL 主页可访问，再实现业务功能。
11. 备份仅使用本机 cron（独立 `/etc/cron.d/wedding`）每小时定时生成并轮转 SQLite 备份，默认保留最近 72 份，不使用 COS、主从或自动灾难恢复；产出目录收束到 `/root/WeddingGift/` 与 `/data/wedding/`。
