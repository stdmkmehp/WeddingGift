# WeddingGift 项目长期约定

- 业务身份：朋友本名全局唯一，不处理同名；同一成员可配置本名及零到多个日常昵称作为登录名称，所有登录名称规范化后全局唯一。
- 卡片密钥：由项目所有者人工生成，严格为 8 位 ASCII 数字；一个密钥最多绑定一个同行组，一个成员只属于一个同行组；一个同行组可绑定多个密钥（2026-09-13 调整，防登录名称被冒名首绑后本人无法补绑），同组使用任一已绑定密钥看到同一份回礼；「密钥已绑定其他同行组」登录失败对外明确提示可联系新郎处理（`401 + key_already_bound`），名称/密钥无效仍为统一模糊错误。
- 版本兼容偏好（2026-09-13 定）：除非用户明确要求，否则不需要考虑版本兼容性问题——schema/接口等变更直接改源头（如直接修订 0001_init.sql）并重置数据库，不写独立迁移文件、不做升级路径兼容。
- 礼品：首批类型为旅游年卡、电影券、咖啡券；同行组可拥有多份礼品，类型可扩展，礼品实例可覆盖类型默认兑换信息。
- 架构原则：小范围、低并发、低数据量，优先核心功能并避免过度设计。采用 Go 单体、单实例 SQLite 和本机 cron 备份；不做 COS、主从、高可用、复杂恢复、重审计或高并发体系。
- 依赖与镜像发布（2026-09-13 修订）：仓库不维护 `vendor/`，Dockerfile 构建阶段为 `go mod download`（需网络）。正式机构建机无法直达 Go 模块源/镜像源，因此**镜像一律开发机 `ops/build-image.sh` 构建打包（`docker save` + gzip 到 `dist/wedding-app-<version>-<commit>-<TS>.tar.gz`，`dist/` 已 gitignore）→ scp 到正式机 → `ops/load-image.sh` 解压 load**；正式机禁止 compose build（必失败）。升级依赖流程：开发机 `go mod tidy` 后随代码提交。
- ops 脚本职责划分（2026-09-13）：`stop-app.sh`/`start-app.sh` 独立负责停/起服（幂等）；`reset-db.sh`/`restore-db.sh` **仅操作数据库**——不停起服，容器运行中直接报错拒绝执行，restore 失败回滚只恢复文件状态不自动起服，起服由操作者显式执行。
- 备份约定：SQLite online backup API（非裸 dump）；宿主机独立 `/etc/cron.d/wedding`（不动 Costra 两个 cron 文件），每小时 `:44` 触发、保留最近 72 份（≈3 天）；:44 用于避开整点 pg_dump、:47 主从检查、06:27 刷新、23:5x 分析窗口。健康检查用应用自带 `wedding healthz-check` 子命令（兼容 distroless/scratch）。
- 目录收束约定（2026-09-12 更正）：WeddingGift 全部产出集中到两处根目录——`/root/WeddingGift/`（staging 实际 git clone 位置：代码/compose/脚本/cron 与 nginx 片段仓库副本）与 `/data/wedding/`（data/backups/secrets/import/nginx 子目录）；应用日志走 Docker json-file，不散落其他位置。`app.key` 离线异位保管，重要性等同或高于数据库备份。
- 目录权限模型（2026-09-12 上机实测后修正）：容器内进程恒为 UID 65534 且 cap_drop ALL，bind mount 保留宿主机属主/权限位。`/data/wedding` 顶层与 `import` 必须 root:root `0755`（65534 需穿越顶层并读取 import 内 0644 CSV，`0700` 会全链路 EACCES）；`data`/`backups`/`secrets` 为 `65534:65534` `0700`；`nginx` 为 root:root `0700` 且不进容器。已固化在 `ops/deploy-app.sh` 与 06-m6-runbook §2.3、02 架构 §13.1（v2.2）。
- 回归与验证方式（2026-09-14 定）：`ops/test.sh`、`ops/verify-public.sh`、`ops/canary-smoke.sh`、`ops/staging-selfcheck.sh` 已删除，不再维护任何自动化验证脚本。本地回归用显式命令（`gofmt -l .` / `go vet ./...` / `go test -race ./...` / `CGO_ENABLED=0 go build` / `go run ./cmd/wedding data validate --dir testdata/fixtures`，见 README「M6 质量收口与正式开放」）；前端危险 API（`innerHTML` 等）、外部资源、持久存储与秘密按代码约定人工 + CR 把关；上机自检与发布后的真实 URL / canary 验证按 `docs/06-m6-runbook.md` §2.2 / §4.1 / §4.2 的人工核对清单执行。
- 开发顺序：先实现最小主页，再通过 `https://stg.costra.cloud/wedding/` 验证真实访问链路，之后开发数据、鉴权和多礼品功能。
- 部署边界：WeddingGift 与 Costra 数据严格隔离；Costra 既有主从与热备仅是共享机器事实，不属于 WeddingGift 架构。
- 实体礼品卡视觉偏好（2026-09-13）：整体应温馨、清新、克制且有高级感，避免模板化大红婚庆与装饰堆砌；已确定且仅保留 A「幕启·相见」主题，作为后续正反面制稿唯一方向。酒杯、爱心与鲜花须以低饱和轻盈线稿分散并洋溢于正反面边缘，可局部出血，但必须避开人脸、文字、QR 静区及刮刮密钥功能区。
- 新人署名（2026-09-13）：新郎为赵伟，新娘为刘子璇；实体礼品卡正反面统一使用 `赵伟 & 刘子璇`，正面主文案定为「把相见，留成一份心意」，背面感谢文案已随 `docs/06-gift-card-design-brief.md` v1.4 定稿。
- 婚礼日期（2026-09-13 定稿）：`2026-09-26`；`internal/app/config.go` 中 `WEDDING_COUPLE_NAMES`/`WEDDING_DATE` 默认值已改为真实定稿值（compose 不覆盖，默认值即线上值）。
- 网页版式（2026-09-13 定，2026-09-13 修正）：登录页顶部顺序——`home-intro`（`感谢你来见证我们的幸福时刻`）作为主标题居中、在 `site-header`（`赵伟 & 刘子璇 / 2026-09-26`）之上；登录表单跟随后两者之下。登录后礼品视图按「感谢信」排版——称呼「致 xxx」**居中**作为礼品页主标题（2026-09-13 由原居左改为居中），致谢正文之下为居右落款（新人署名一行、婚期紧随其后，落款位于 custom-message 之后）；顶部抬头（`home-intro + site-header`）进入礼品态即隐藏——`home-intro` 仅登录态可见，`site-header` 在登录/加载/异常态保留。
- 婚礼网页视觉定稿（2026-09-13 定稿，2026-09-14 v1.8 重设计，docs/01 同步）：①登录页以半透明新人合照 `web/assets/photos/couple.jpg` 作上半渐隐背景（仅登录态显示，缺失时静默降级）；②灰粉酒红双帷幕仍分置左上/右上，并改为多层柔光曲面；③边缘装饰改为**被视口裁切的 5 组大比例手绘花艺构图**——左上双朵山茶、右上碰杯高脚杯、右侧花藤心形、左侧舒展大花、右下枝条花苞，沿对角线平衡分布且避开中央信息区；使用玫瑰粉、柔粉、鼠尾草绿、香槟金细描边/断续金线，禁用零散通用小图标或连续花边；④「喜」字改为极淡细线印章；⑤5 片全局飘落的 SVG 花瓣为 24–34px，带双瓣凹口、内侧高光与叶脉，19–25s 缓慢下落并轻柔摆动（不整周翻转），`prefers-reduced-motion` 时静止不可见；窄屏通过缩小画板与加大视口外裁切，绝不遮挡输入控件、正文或礼品卡。整体目标是温馨、清新、克制且有高级设计感。
- 实体礼品卡图片规格（2026-09-13）：正、反面成品图片均固定为 `1710 × 1080 px`（裁切成品、无出血，`20 px/mm`，约 `508 ppi`）；如交付栅格印刷稿，带 `1.5 mm` 出血画板为 `1770 × 1140 px`。该约定已写入设计 Brief v1.5。
- AI 礼品卡底图规范（2026-09-13）：`docs/07-gift-card-ai-base-art-prompts.md` 定义正、反面分别生成的可复制提示词。AI 只生成「幕启·相见」框架与边缘装饰，严禁生成任何文案、合照、QR、网址、8 位密钥或刮刮层；按 `1770 × 1140 px` 输出，中央 `1710 × 1080 px` 为成品卡面，四周各 `30 px` 为纯暖白外扩留白区。该 `30 px` 外扩尺寸与印刷交付的 `1.5 mm / 30 px` 出血一致，最终交印仍须按设计 Brief 完成制版。
